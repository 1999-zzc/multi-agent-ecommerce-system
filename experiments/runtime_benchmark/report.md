# 调度与故障注入：


## 串并行对比

每模式 200 次计时调用、20 次预热，10 并发；每轮 100 次，共两轮，执行顺序为串行/并行、并行/串行。
同一图、同一数据、同一延迟种子。串行对照仅把图模块中的 gather 替换成顺序等待；生产文件未改。
延迟为进入执行槽后的整条 graph.ainvoke 耗时；包含 LangGraph 开销，不包含应用外部排队和 HTTP。


AVG 降低 17.48%，P95 降低 16.00%。


## 故障注入

8 类故障，每类每模式 20 次调用：10 次首次失败后恢复、10 次持续失败。每模式共 160 次，两模式总计 320 次。
对照是单次尝试，实验组是当前代码最多总尝试两次；双方保留相同的 Schema 校验和 fallback，不是历史优化前后对照。
保持实际单次 timeout：画像 5 秒，推荐/精排 8 秒，库存 5 秒，文案 10 秒；退避仍为 0.5 秒起步。
故障组采用 20 并发，以便让真实超时同时发生。Invalid schema 被业务层捕获，因此不会自动 retry。

| 故障 | 单次尝试安全可用 | 两次尝试安全可用 | 两次尝试非空 | 两次尝试未校验/缺货商品数 |
|---|---:|---:|---:|---:|
| profile_timeout | 20/20 | 20/20 | 20/20 | 0 |
| redis_unavailable | 20/20 | 20/20 | 20/20 | 0 |
| milvus_unavailable | 0/20 | 10/20 | 10/20 | 0 |
| rerank_timeout | 20/20 | 20/20 | 20/20 | 0 |
| invalid_structured_output | 20/20 | 20/20 | 20/20 | 0 |
| inventory_timeout | 0/20 | 10/20 | 20/20 | 100 |
| marketing_timeout | 20/20 | 20/20 | 20/20 | 0 |
| mysql_unavailable | 0/20 | 10/20 | 10/20 | 0 |

one_attempt：安全可用 100/160 (62.50%)；返回商品 1040 个，其中未通过库存校验或缺货 200 个 (19.23%)。实际 stock<=0 的商品数为 40。

two_attempts：安全可用 130/160 (81.25%)；返回商品 1160 个，其中未通过库存校验或缺货 100 个 (8.62%)。实际 stock<=0 的商品数为 20。

## 判定与边界

- 可用推荐定义：非空、无未处理异常、所有返回商品 stock>0 且被成功的库存结果明确列为可售。
- 不安全仅指本实验能验证的缺货/未通过库存校验，不覆盖交易竞态、违法商品、价格真实性等风险。
- 所有请求都返回结构化结果也可能是空商品或不安全商品；不能用无异常率代替可用率。
- 假商品池为 30 件，其中 6 件缺货；它用于触发控制流，不是此前 2,000 商品的检索效果评测。
- 所有外部连接均被阻止。依赖故障为客户端边界抛异常或挂起，不是关停真实 Redis/Milvus/MySQL 服务。
- 画像走真实 Pydantic 校验；推荐用真实三路组件和融合逻辑，底层 Embedding/检索/仓储由替身返回。
- 第一阶段没有画像，RuleRecall 按当前实现返回空；本轮没有改动该行为。
- 只测试 asyncio 可取消的挂起，不证明 wait_for 可以中断阻塞线程、SQL 驱动或同步 RPC。
- 50% 瞬时、50% 持续故障及八类均匀分布是人为测试配比，不可外推线上可用率。
- 观察到库存结果为空后的放回逻辑时，应记录缺陷，不能据此填写不安全商品率为 0%。
- 没有更改生产代码。本目录新增的基准调用数量不能计作原有单元测试数。
- 复现命令：`.venv/bin/python experiments/runtime_benchmark/run.py`。报告耗时会随机器调度变化。
- requests.json 包含每次调用的实际耗时、最终商品、故障触发、调用计数、取消计数和 Agent 结果。
- results.json 包含运行环境、源文件哈希、汇总值和一致性检查。
